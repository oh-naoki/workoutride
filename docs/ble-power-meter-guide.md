# パワーメーターとのデータのやり取りとデータ抽出のしくみ

このドキュメントは、WorkoutRide がスマートトレーナー／パワーメーターから
**どうやってパワーやケイデンスを受け取り、生のバイト列から数値を取り出しているか**を、
BLE を初めて触る人にも分かるように解説する資料です。

対象コード:
- `frontend/lib/data/ble_connector.dart` … BLE の接続・購読
- `frontend/lib/data/power_meter_data_source.dart` … データ源（実機／モック）
- `frontend/lib/domain/usecase/get_power_meter_data_use_case.dart` … バイト列 → 数値の変換
- `frontend/lib/domain/usecase/get_calculated_power_meter_data_usecase.dart` … 3秒移動平均

---

## 1. まず全体像

パワーメーターは **BLE（Bluetooth Low Energy）** という無線規格でスマホと通信します。
BLE のデータは **GATT** という決まった「棚の構造」で整理されています。

```
デバイス（パワーメーター）
└── Service（サービス）＝ 機能のまとまり
    └── Characteristic（キャラクタリスティック）＝ 実際のデータ1個
        ├── 値（バイト列）
        └── プロパティ（Read / Write / Notify …）
```

- **Service**: 「サイクリングパワー機能」などの大きなまとまり。UUID で識別。
- **Characteristic**: その中の個々のデータ（例: 「今のパワー測定値」）。これも UUID を持つ。
- **プロパティ**: そのデータに何ができるか。今回重要なのは **Notify（通知）**。

> **Notify とは？**
> スマホ側が「値ちょうだい」と毎回聞きに行く（Read）のではなく、
> **デバイス側が値が変わるたびに自動で送りつけてくる**しくみ。
> パワーやケイデンスのように刻々と変わる値は Notify で受け取ります。

WorkoutRide が使う主な UUID:

| 種類 | UUID | 役割 |
|------|------|------|
| Cycling Power **Service** | `0x1818` | サイクリングパワー機能のまとまり |
| Cycling Power **Measurement** | `0x2A63` | パワー・ケイデンス等の測定値（Notify） |
| Battery Service | `0x180F` | 電池残量（スキャン時のフィルタで使用） |

> UUID の `2A63` のような短い形は「16bit UUID」と呼ばれ、正式には
> `00002A63-0000-1000-8000-00805F9B34FB` という128bitの一部です。
> Bluetooth SIG（規格団体）が用途ごとに番号を割り当てています
> （"Assigned Numbers" という一覧表で公開）。

## 2. 接続してデータを受け取るまでの流れ

コードでは次の順で進みます（`ble_connector.dart`）。BLE では**この順番が決まっています**。

```
1. スキャン        FlutterBluePlus.startScan()
      ↓  近くのデバイスを見つける
2. 接続            device.connect()
      ↓  1対1のリンクを張る
3. サービス探索    device.discoverServices()
      ↓  「棚の構造」を読み出す（これをしないと Characteristic を触れない）
4. Notify 登録     characteristic.setNotifyValue(true)
      ↓  「値が変わったら送って」と依頼
5. 受信            characteristic.onValueReceived → Stream<List<int>>
         値が届くたびに List<int>（＝バイト列）が流れてくる
```

`notify(String uuid)` メソッドが 2〜5 をまとめて行い、
**バイト列のストリーム `Stream<List<int>>`** を返します。

```dart
// power_meter_data_source.dart
Stream<List<int>> getRawData() => _bleConnector.notify("2A63");
```

ここで得られる `List<int>` の1要素は **1バイト（0〜255）** です。
たとえば `[0x20, 0x00, 0xC8, 0x00, ...]` のような並びが1回の通知で届きます。
**この生バイト列から意味のある数値を取り出すのが、次章の「データ抽出」です。**

## 3. Cycling Power Measurement (0x2A63) のパケット構造

`0x2A63` の中身は Bluetooth SIG の仕様（Cycling Power Service / GATT Specification
Supplement）で**バイトの並び順が厳密に決められています**。ポイントは2つ:

1. **先頭に「フラグ」があり、後ろにどんなデータが入っているかを教えてくれる**
2. **数値は「リトルエンディアン」＝下位バイトが先**

### パケットの並び

```
バイト:  0        1        2        3        4          5          6          7
        [フラグ下][フラグ上][パワー下][パワー上][回転数下 ][回転数上 ][時刻下   ][時刻上   ]
         └── Flags(16bit)┘ └ Instantaneous Power ┘ └── Crank Revolution Data（任意）──┘
```

- **Flags（2バイト・必須）**: 後続にどのフィールドがあるかを示すビットの集まり
- **Instantaneous Power（2バイト・必須）**: 今のパワー[W]
- そのあとに、フラグで「ある」と示されたフィールドだけが順番に続く（**可変長**）

### フラグのビットの意味（抜粋）

| ビット | 16進 | 意味 | 追加されるデータ |
|--------|------|------|------------------|
| bit 0 | `0x001` | Pedal Power Balance あり | 1バイト |
| bit 4 | `0x010` | Wheel Revolution Data あり | 6バイト |
| **bit 5** | **`0x020`** | **Crank Revolution Data あり** | **4バイト（回転数2＋時刻2）** |

ケイデンス（クランク回転）に使うのは **bit 5** です。
だからコードは `flags & 0x020` で「クランクデータが入っているか？」を判定します。

> **なぜフラグが必要？**
> パワーだけ送るデバイスもあれば、ケイデンスやトルクも送るデバイスもあります。
> パケット長を固定にすると無駄が多いので、「入っているものだけ詰めて、
> 何が入っているかは先頭のフラグで知らせる」という設計になっています。
> そのため**受信側はフラグを見て、読む位置（オフセット）を進めながら解釈**します。

## 4. バイト列から「パワー」を取り出す

リトルエンディアン（下位バイトが先）なので、2バイトの数値はこう組み立てます。

```dart
int flags = (value[1] << 8) | value[0];          // 先頭2バイト＝フラグ
int instantaneousPower = (value[3] << 8) | value[2];  // 次の2バイト＝パワー
```

`<< 8` は「上位バイトを8bit左にずらす」＝256倍の位置に置く操作、
`|`（OR）で下位バイトと合体させます。

**具体例**: `[0x20, 0x00, 0xC8, 0x00, ...]`
- パワー = `(0x00 << 8) | 0xC8` = `0 | 200` = **200 W**

読み取った分だけ「今どこを読んでいるか」を表す `index` を進めていくのが
パース（解析）の基本です。フラグで示された任意フィールドがあれば、
その分だけ `index` を飛ばします。

## 5. 「ケイデンス」を取り出す ― ここが少し難しい

ケイデンス（クランクの回転数 rpm）は、パワーのように**そのままの値は送られてきません**。
代わりに次の2つが送られます（bit 5 が立っているとき）。

| フィールド | 型 | 意味 |
|------------|----|----|
| Cumulative Crank Revolutions | uint16 | **電源投入からの累積**クランク回転数 |
| Last Crank Event Time | uint16 | 最後にクランクが回った**時刻**。単位は **1/1024 秒** |

つまり「積算値」と「その時刻」だけが来るので、
**2回の通知の差分をとって自分で rpm を計算**します。

```
                 (今回の回転数 − 前回の回転数)
rpm = ──────────────────────────────────────────── × 60
       (今回の時刻 − 前回の時刻) ÷ 1024   ← 秒に直す
```

コード（考え方）:

```dart
int revDiff  = 今回の累積回転数 - 前回の累積回転数;  // 何回転増えたか
int timeDiff = 今回の時刻       - 前回の時刻;        // その間の時間（1/1024秒単位）
double rpm   = revDiff * 60 / (timeDiff / 1024);
```

**具体例**: 前回（回転数 100, 時刻 0）→ 今回（回転数 103, 時刻 2048）
- revDiff = 3 回転
- timeDiff = 2048 → 秒に直すと 2048 / 1024 = **2 秒**
- rpm = 3 ÷ 2 × 60 = **90 rpm**

> **なぜ「時刻」も送るの？ 1秒ごとじゃないの？**
> 通知が届く間隔は一定とは限らず、無線なので遅延・ゆらぎもあります。
> 「回転数だけ」だと正確な rpm は出せません。
> デバイスが**クランクが回った正確な時刻**を一緒に送ることで、
> 受信タイミングがぶれても正しい回転数を計算できます。

## 6. 実装上の落とし穴（＝実際にあった不具合）

ケイデンス計算には、初学者がハマりやすい2つの罠があります。
WorkoutRide でも実際に「90rpmで回しているのに一瞬60rpmに落ちる」不具合として発生しました
（PR #90 で修正）。

### 罠その1: 「新しい回転が無い通知」で 0 にしてしまう

デバイスはクランクが1回転するより**速く**通知を送ることがあります。
その場合、前回と回転数・時刻が**同じ**通知（`revDiff == 0`）が届きます。

ここで「回転が無い＝ケイデンス0」としてしまうと、
直後の**3秒移動平均**（`get_calculated_power_meter_data_usecase.dart`）で:

```
直近3サンプルが {90, 90, 0}  →  平均 (90+90+0)/3 = 60
```

となり、**一瞬だけ 60rpm に落ちて見える**わけです。これが不具合の正体でした。

**対策**: 新しい回転イベントが無い通知では **0 にせず、直前のケイデンスを保持**する。
ただし本当に止まったとき下がらなくなるので、
**一定時間（3秒）新しい回転が来なければ 0 にする**という停止判定を入れます。

### 罠その2: 16bit の「一周（ラップアラウンド）」

`Last Crank Event Time` は uint16 = **0〜65535** の範囲しかありません。
単位が 1/1024 秒なので、65536 / 1024 ≒ **約64秒で最大値に達し、0 に戻ります**。
`Cumulative Crank Revolutions` も同じく 65535 の次は 0 に戻ります。

素朴に引き算すると、一周をまたいだ瞬間にこうなります:

```
前回の時刻 = 65000, 今回の時刻 = 1512（一周して戻ってきた）
timeDiff = 1512 - 65000 = -63488  ← 巨大な負の数！ → rpm が異常値に
```

**対策**: 差分を **16bit にマスク（`& 0xFFFF`）** します。

```dart
int timeDiff = (今回の時刻 - 前回の時刻) & 0xFFFF;  // 常に 0〜65535 に収まる
int revDiff  = (今回の回転数 - 前回の回転数) & 0xFFFF;
```

こうすると `(1512 - 65000) & 0xFFFF = 2048` となり、正しく「2秒」と解釈できます。
これは Bluetooth の仕様でも想定されている、**カウンタが一周する前提の正しい引き算**です。

### （補足）初回の通知

累積値は「電源投入からの合計」なので、**最初の1通知だけでは差分が計算できません**
（比較する前回値が無い）。最初は 0 を返し、2回目以降から計算します。
これを忘れると、初回に巨大な累積値がそのまま差分になって異常値が出ます。

## 7. データが画面に届くまでの流れ（まとめ）

```
[パワーメーター]
   │  BLE Notify（0x2A63 のバイト列）
   ▼
BleConnector.notify("2A63")            … Stream<List<int>>（生バイト列）
   ▼
BlePowerMeterDataSource.getRawData()   … 生バイト列をそのまま流す
   ▼
GetPowerMeterDataUseCase.processData() … ★バイト列 → {power, cadence} に変換
   │                                       - フラグを見て読む位置を決める
   │                                       - パワーを組み立てる
   │                                       - 差分からケイデンスを計算
   │                                       - 16bitラップ対応／0埋め回避（第6章）
   ▼
GetCalculatedPowerMeterDataUseCase()   … 直近3秒の移動平均で滑らかに
   ▼
WorkoutScreenStateNotifier             … state に反映
   ▼
[メーター表示]
```

## 8. 用語集

| 用語 | 意味 |
|------|------|
| BLE | Bluetooth Low Energy。省電力の近距離無線。 |
| GATT | BLE のデータ構造の決まり（Service > Characteristic の階層）。 |
| Service | 機能のまとまり。UUID で識別。 |
| Characteristic | 個々のデータ。UUID とプロパティ（Read/Write/Notify）を持つ。 |
| Notify | 値が変わるたびにデバイスから自動送信されるしくみ。 |
| UUID | データや機能を識別する番号。16bitの短縮形（例 `2A63`）がよく使われる。 |
| リトルエンディアン | 数値を「下位バイトが先」に並べる方式。BLE の数値はこれ。 |
| フラグ | パケット先頭にあり、後続にどのデータが入っているかを示すビット群。 |
| 累積値（Cumulative） | 電源投入からの合計。差分をとって使う。 |
| ラップアラウンド | カウンタが最大値を超えて 0 に戻ること。差分計算で要注意。 |

## 9. 参考（一次情報）

BLE の正確な仕様は **Bluetooth SIG** が公開しています（無料・登録で閲覧可）。

- **Cycling Power Service** — Service `0x1818`、Cycling Power Measurement `0x2A63` の
  フィールド定義・フラグのビット割り当て。
- **GATT Specification Supplement** — 各 Characteristic のバイト構造の詳細。
- **Assigned Numbers** — UUID（Service / Characteristic）の割り当て一覧。
- （関連）**Cycling Speed and Cadence Service** `0x1816` / CSC Measurement `0x2A5B`
  — 別方式でケイデンスを送るデバイス向け。考え方（累積回転数＋時刻の差分）は同じ。

> 実装で迷ったら、まず 0x2A63 の **フラグのビット定義**と、
> 各フィールドの**型（uint16 など）と単位（1/1024秒）**を仕様で確認するのが近道です。
